# Try Buzz first; nothing fully fits

**No existing application fully meets this need as of 2026-11-06.** The ranked top 3 are **(1) Buzz by Block with a self-hosted local relay, (2) agentchattr, and (3) a local Mattermost server with its built-in MCP (Model Context Protocol) server, used in prompt-driven mode.** None documents the Claude and Codex desktop apps as live participants that respond by themselves. Buzz comes closest overall: it has real channels, per-channel agent membership, and Claude and Codex signed in with your subscriptions, but it runs its own copies of the vendor runtimes and is still a pre-1.0 preview. agentchattr is the simplest and most private way to get live agent-to-agent chat, but it wakes agents by typing into CLI sessions in tmux. Mattermost is the only pick that uses your actual desktop apps with no model CLI, but agents act only when someone prompts them. **My recommendation is to try Buzz directly, fall back to agentchattr, and build your own only if participation through the desktop apps themselves is non-negotiable.** Building will not remove the main obstacle, because the wake limit sits in the desktop apps, so test that first. Nothing here was installed or run: every finding rests on documentation, source code, and issue reports, and independent reviews are almost absent across the category.

## One missing wake path explains why every tool falls short

Chat rooms are easy to find. The hard part is getting a desktop app to start a turn when a message arrives. Anthropic's documentation says a standard MCP server only answers queries during a task and pushes nothing into the session ([Claude Code channels](https://code.claude.com/docs/en/channels)). Claude's local push route, channels, is a research preview that is set up through the `claude` terminal command, and custom channels need a development flag that works only in interactive sessions ([channels reference](https://code.claude.com/docs/en/channels-reference.md)). Codex has a push mechanism in its app server, but that is started with `codex app-server`, and OpenAI's docs do not say whether the desktop app shares it ([Codex app server](https://learn.chatgpt.com/docs/app-server)). This research could not confirm that any third party can start a turn in either desktop app without a CLI.

As a result, tools split into three camps. Some inject prompts into terminal sessions or spawn CLIs, which works reliably but uses CLIs. Some use a polling or long-wait loop, which might suit desktop apps but has no evidence of holding up there. The rest connect desktop apps over plain MCP, which works only on demand. The table scores the top 3 against your need; the grades are my judgment from the evidence below.

| Subscription, no API keys | Yes, per docs and code | Yes by inference from its design | Yes by inference; chat token only |

## Three picks, each missing something different

### Buzz wins on fit despite preview-grade stability

Buzz is the only packaged product with verified Slack-like channels, threads, direct messages, private channels, and agents added to a channel the same way as people ([block/buzz](https://github.com/block/buzz)). Its current preview installs Buzz's own copy of Claude (about 250 MB) and Codex (about 130 MB), then signs you in through the browser with your Claude or ChatGPT account. Those agents run on your Mac while Buzz is open ([block/buzz-app](https://github.com/block/buzz-app)). The desktop source contains a Claude subscription login path, and onboarding names both subscriptions ([agent_auth.rs](https://github.com/block/buzz/blob/main/desktop/src-tauri/src/commands/agent_auth.rs), [SetupStep.tsx](https://github.com/block/buzz/blob/main/desktop/src/features/onboarding/ui/SetupStep.tsx)). The help docs describe agent-to-agent dispatches and handoffs, teams of up to 32 members, and a bundled Codex review tool ([Buzz help](https://github.com/block/buzz-app/blob/main/docs/buzz-help.md)). It is free and Apache-2.0, with 36,776 stars and very active development.

The misses are substantial. **It does not use your desktop apps or their sessions,** so your existing conversations and context in those apps are not in the room. **Privacy holds only with a self-hosted relay:** hosted communities send data to Block, and the local recipe needs Docker with Postgres, Redis, and MinIO ([block/buzz](https://github.com/block/buzz)). The newer app steers new users toward communities, and this research did not confirm that the 0.7 preview works smoothly against a local relay. That is the first thing to test, because the local-relay instructions and the cleanest subscription flow live in two different app lines. Telemetry and update traffic to Block were also not checked.

Stability is the other concern. An open bug filed 2026-10-29 reports a local Claude agent waking only on its owner's @mentions, which leaves agent-to-agent waking unsettled ([issue #8684](https://github.com/block/buzz/issues/8684)). Agents work in `~/.buzz` by default, and a request for extra per-agent folders is still open, so pointing agents at your repositories needs checking ([Buzz issues](https://github.com/block/buzz/issues?q=additionalDirectories)). The channel-topic call was unimplemented as of a July write-up, and the current status is unconfirmed. That same review called Buzz "not a mature product" and suggested waiting if you want a Slack replacement today ([Developers Digest](https://www.developersdigest.tech/blog/buzz-block-agent-native-messaging-nostr)). Older harness docs also still call for API keys, in conflict with the desktop flow ([buzz-acp README](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)).

Subscription terms deserve a flag too. Anthropic allows you to sign in to its unmodified Claude Code binary with your own subscription, but restricts third-party apps from offering Claude.ai login or routing requests through plan credentials ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Buzz's flow sits close to that line. I read it as an unresolved risk, not a violation. Public signals are modest and early: a Product Hunt launch with 166 upvotes ([Hunted.space](https://hunted.space/product/buzz-3)) and a positive but small Hacker News thread, read through a mirror ([HN mirror](https://sites-zeta.vercel.app/item/48632977)).

### agentchattr is the cleanest local option if you accept CLIs

agentchattr is designed for localhost, with channels you can create, rename, and delete, @mentions, and direct agent-to-agent conversation governed by a per-channel loop guard ([agentchattr](https://github.com/bcurts/agentchattr)). Agents connect over HTTP MCP at `127.0.0.1:8200/mcp`, and it needs no account of its own. It is MIT-licensed with 1,583 stars and was last pushed 2026-10-24, and it requires only Python 3.11+ and tmux on a Mac. That makes it the strongest pick on your data rule, with much less to run than Buzz.

**It misses the desktop-app requirement outright:** a wrapper wakes agents by injecting prompts into their terminal sessions, and neither desktop app is mentioned. An app could probably read and post through the HTTP endpoint, since Codex supports streamable HTTP, but it would not wake automatically ([Codex MCP docs](https://developers.openai.com/codex/mcp)). **Per-room membership and topics were not confirmed** in what was read, so your room-control requirement is open. Its latest release is v0.5.0 from July 2026, and no independent review or security audit was found. Popularity here means interest, not proof of reliability.

### Mattermost is the proven workspace, but agents only act when prompted

Mattermost is the only pick that honors "installed apps, subscriptions, no model CLI" with a mature chat product behind it. Its first-party Agents plugin includes an MCP server with claimed 100+ tools, and its README names Claude Desktop and Claude Code as clients ([mattermost-plugin-agents](https://github.com/mattermost/mattermost-plugin-agents)). OpenAI says the ChatGPT desktop app, Codex CLI, and IDE extension share MCP configuration over stdio or streamable HTTP ([OpenAI MCP docs](https://learn.chatgpt.com/docs/extend/mcp.md?surface=cli)). Because agents inherit their user's permissions ([Mattermost blog](https://mattermost.com/blog/mattermost-mcp-server/)), a separate account per agent should make channel membership a real access boundary. That is stronger per-room control than the agent-native tools offer, though it is my inference.

**The miss is the core experience: there is no wake and no live debate.** You would prompt each app to read the room and reply, so it works as a shared record you relay through by hand. Mattermost's own bots do reply on mention, but they are plugin-run bots on admin-configured models, which likely means API keys, and channel auto-reply needs Enterprise Advanced ([Mattermost user guide](https://docs.mattermost.com/agents/docs/user_guide.html)).

Setup is also unproven. Claude's normal connector route comes from Anthropic's cloud and cannot reach a private localhost server, so Claude needs a local entry in its config file, probably with a wrapper ([Anthropic help](https://support.claude.com/en/articles/11503834-building-custom-connectors-via-remote-mcp-servers)). No source shows Codex connected to this server. Mattermost is documented as Linux binaries, so a Mac means running containers. The biggest licensing question is whether the plugin works on Team Edition, since the editions page lists agents under Entry and higher. Entry caps visible history at 10,000 messages across all channels, which chatty agents would reach quickly ([editions docs](https://docs.mattermost.com/product-overview/editions-and-offerings)). That cap also drives the sharpest independent complaints, including users calling it fake open source and leaving after years of use ([Mattermost forum](https://forum.mattermost.com/t/10000-self-host-cap/25374)).

## Use one directly unless desktop-app participation is non-negotiable

Your answer depends on how you treat "ideally no model CLIs." **If subscription reuse is the real goal, use a tool directly and do not build yet.** The Buzz and agentchattr runtimes are vendor binaries signed in with your own accounts, and your Mac already has `codex-cli` inside `ChatGPT.app`, so the practical difference may be small. Start with a short trial of Buzz: run the local relay, connect the 0.7 preview, add Claude and Codex to a private channel, confirm that one agent's @mention wakes the other, point both at a test repository, and watch outbound traffic for Block endpoints. Restrict it to the Claude and Codex harnesses so that no other provider enters. If the relay stack or preview bugs get in the way, move to agentchattr and check whether it can limit a channel to chosen agents.

**If participation must go through `Claude.app` and `ChatGPT.app` themselves, as your draft Parley requirements state, then only building (or Mattermost in manual mode) qualifies.** Even then, run the wake test before writing the product. Keep each app in a long-running wait or polling loop against a minimal local MCP server, and measure how long it survives, how much allowance it burns, and whether prompts interrupt it. The closest evidence is thin: walkie-talkie's wait lasts up to an hour, but its survival under desktop-app tool timeouts is unknown ([walkie-talkie](https://github.com/suruseas/walkie-talkie)). Anthropic's cross-session messaging suggests a real local push into Desktop sessions, but only on the Claude side ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)). If the loop fails on either app, your own build fails in the same way, and you are back to CLI-based wake.

If the test passes, forking agentchattr may be cheaper than starting from nothing. Its MIT license, localhost MCP endpoint, channels, and loop guard cover much of what you would otherwise write, leaving a wait tool, human-only membership, and permission handling to add. I have not read its code, so confirm that it is a good base. Whichever route you pick, three risks stay with you. Full-access agents reading each other's messages form a prompt-injection path, which [crewchat's README](https://github.com/deepankar17/crewchat) states openly. Your rule on third-party data still relies on agents following instructions. And every agent turn draws on plan limits, which Anthropic says assume ordinary individual use ([Anthropic legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)).

## Conclusion

The market has already built the part you were about to build first. Local channels, mentions, and loop guards are available off the shelf, while the piece that does not exist is the one no chat app can supply on its own: an outside event starting a turn inside a desktop app. So the build-or-use decision is really a test of that one mechanism, and a small experiment can answer it before any product work begins.

Your four criteria also pull against one another here. Popularity tracks poor fit, since the most starred tools are orchestrators, and the best-fitting tools have the least independent evidence. No source shows a human, Claude, and Codex working in sustained multi-room use on any of these products, so treat any choice as a trial, and expect this list to age quickly: Buzz's 1.0 beta or a vendor's change to desktop wake could reorder it within months.
