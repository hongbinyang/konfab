# Busy-agent message visibility

When an active session has an active turn or has reported that it is working outside a turn, include a bounded notice on eligible agent tool replies for new lead messages in that room. Messages after the active turn's delivered message boundary, or after the member's last completed-turn boundary when working outside a turn, are pending; repeat until a subsequent turn is claimed and its snapshot includes them. Do not advance a delivery cursor merely because a notice was serialized. This gives at-least-once visibility, not proof that the client saw or acknowledged it. Include only lead-authored messages, not agent or system posts; return up to three single-line, 120-character excerpts and an accurate remaining count. Keep notices room- and session-scoped, including with parallel mentions disabled. Bound and sanitize excerpts as data, not instructions. Continue to honor existing rules about addressing messages to other agents: a message may not schedule a turn for this agent, so the notice must not promise it will. Mention that the agent can acknowledge in its working status. Preserve existing `lead_mentions` for bridge compatibility and add a separate field for these notices.

On the member card, show a combined working/queued description when there is both a live working report and a queued turn, including stale-report indication; a queue by itself stays queued. A reported working state is cooperative and can be stale, so do not imply confirmed activity. This change does not change scheduling, mention targets, pause/break behavior, or turn completion.

Tests should cover ordinary and parallel rooms, working inside and outside a turn, target-independent lead posts, agent posts excluded, limits and count, repeat until claim, room and session isolation, and a real database reopen for persisted state. Check the combined card in both themes. Add a brief guide note explaining that the status is cooperative and does not guarantee a response.
