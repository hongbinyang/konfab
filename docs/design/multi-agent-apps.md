# Multiple agents per desktop app

An app credential identifies an app, while each agent remains an independently named room participant. A conversation joins a room as a specific agent and receives an opaque session ID. Rejoining the same agent in the same room replaces only that agent's previous session; different agents can remain connected concurrently. Ordinary turns are serialized; the later opt-in [parallel lead-mentions prototype](parallel-lead.md) permits additional explicitly addressed turns.

## Persistence and migration

Add an `apps` table with a stable app ID, display name, credential hash and default agent ID; add an app foreign key and an archived timestamp to `agents`. Migrate every existing agent to an app of the same ID, with itself as default and its existing token hash copied to the app credential. Preserve IDs and all references, room membership, sessions, roles and history; do not regenerate credentials. Update setup/rotation/recovery to treat the app credential as authoritative without changing the already installed connector config. Configured apps added on a later startup also get an app and default agent idempotently. Keep app-specific run hours inherited by its agents unless explicitly overridden. Migration and token setup must be transactional and covered by reopen/upgrade tests.

Agent IDs are globally unique, immutable mention targets validated on creation; an editable display name is separate, so renaming cannot break `@mentions`, sessions or history. New IDs default to `<app>-<label>`. Soft-archive non-default agents so old messages and events retain their identity; block removal while any active session exists and detach the agent from current room membership and queued work in a single transaction. Never allow the app's default agent to be removed. Historical names and audit records remain available. Enforce the configured per-app maximum transactionally, counting non-archived agents including the default. To avoid breaking the existing `agents` map in config, put the default-four limit under a new `multi_agent.max_per_app` setting; lowering the limit does not delete existing agents. The Add agent form joins the new identity to the current room by default, and suggests an available ID.

## Authentication and bridge

The bearer token authenticates an app. Extend `join_room` and `/agent/join` with optional `as`; absent means that app's default. The server verifies the target is an unarchived agent owned by that authenticated app and a member of the requested room. The bridge forwards `as` and does not keep a process-global selected agent. All other calls carry their existing `session_id`; the server resolves the session's agent and verifies it belongs to the authenticated app before passing it to the existing service methods. Turn IDs, permission requests, request receipts, progress and handoff checks remain bound to that resolved agent/session; closed and replaced sessions retain their existing statuses. Reuse of an app credential trusts its conversations to act for any agent in that app, so this is organization rather than isolation between those conversations. Other apps' agents and sessions must be rejected.

Existing connector configuration and default-agent prompts continue to work unchanged. An already-running old bridge lacks the new `as` tool argument, so opening a named agent requires loading the updated bridge/tool schema; provide a clear reload/rejoin instruction rather than claiming the old bridge can select agents. The server must retain compatibility with old default-agent clients. Agent-specific join prompts explicitly name the target and the room.

## Interface

> Superseded by [agents first](agent-first.md): agents are now added from one form that picks the app and an optional room role, and cards show App and Role chips instead of app groups.

Group agents under their app in the management UI, with Add agent, an editable display name, a visible app badge and copyable per-agent join prompts on room cards. Leave existing room member selection, role assignment, team roles and per-agent status usable with the new agents. Show limit and removal errors clearly; keep a room's existing selected members unchanged when creating an agent. Removing an active agent is blocked with a clear explanation. The guide explains separate conversations, shared account allowance, permissions and the shared-credential trust model.

## Validation

Test migration of existing tokens/defaults and existing sessions through a database and server reopen; old joins without `as`; concurrent distinct-agent joins and interleaved waits/posts/permission requests; same-agent rejoin replacement; cross-app session and agent rejection; request receipt isolation; per-app limit and configuration; add/rename/archive, refusal to remove active/default agents, and preservation of history; room membership, prompts and app badges. Exercise the UI in an isolated browser, and run `npm run check` before commit. Review this design before implementing the interface.
