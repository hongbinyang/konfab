# Advisory write locks and structured formats

## Advisory write locks

Locks are local coordination records, not filesystem, sandbox or GitHub enforcement. A global resource key identifies the shared thing across rooms (for example `repo:/absolute/path#main`); callers must use the same explicit key. Repository keys resolve existing absolute paths to their real path and preserve case-sensitive branch names; room rules provide a suggested main-branch key when a project folder is set. Store `resource` (unique primary key), holder agent and session, room, purpose, acquired time and lease expiry. Validate bounded resource/purpose text. Acquire in a transaction: require a live session in an unarchived room and `can_edit`, discard expired or ended-session records, grant if free, or return the current holder and expiry. The same session may renew; a different session, including another session of the same agent, cannot release or renew it. Use a bounded lease with 30 minutes as default and a four-hour maximum. A release by its holder is idempotent; an expired lease is not proof that work has stopped. Session replacement, end, removal and room archival release affected records in their existing transactions. Expiry is checked on access and by the server tick; restart recovers records for still-live sessions and expires stale records. No user data or token leaves the local server.

Add `acquire_lock` and `release_lock` bridge tools with `session_id`, resource, purpose and optional lease duration; routes resolve agent identity from the authenticated session. Durable request IDs and transactions prevent retry from granting a second holder. Add the advisory instruction to the agent's room rules, expose active locks on member cards and in activity, and let the lead force-release with a system-labelled room message and audit event. UI and guide must state that the lock cannot stop writes or pushes by external tools, and that users choose matching resource keys.

## Review and debate runs

Persist one active or paused format run per room, including format, topic, rounds, slots and current step. Persist an ordered step plan with round, slot, agent, state, and linked turn ID so retry, rejoin, skip and restart do not advance twice. Review uses author, one to three distinct reviewers and 1–N bounded rounds: author introduction, each reviewer and an author response for each round, followed by an author summary. Debate uses distinct pro, con and judge: pro/con in each round, then judge verdict. Topic is lead-provided context, not an instruction granting authority. Roles and edit permissions are unchanged.

Starting validates live room membership, distinct slot assignments and a bounded topic, and records the plan transactionally. Each step is scheduled as a normal queued turn explicitly linked to the step; its `wait_for_turn` result includes a replayable format banner and a system-labelled round marker. The existing one-active-turn-per-room constraint remains. While a run is active, the scheduler gives precedence to its current step and defers ordinary queued turns rather than deleting them. Agent `next` and mentions do not override the format sequence; after the run, ordinary routing resumes. Lead posts remain allowed and are delivered through normal message history; queued ordinary work is retained. The slot's next step is enqueued only after an accepted post, pass or explicit lead skip, in the same transaction as step completion; a pass cannot be mistaken for a written summary. Final author/judge text is saved as a decision proposal, never auto-confirmed; if the final step is passed or skipped, finish without inventing a decision and notify the lead.

Pause prevents starting the next format step but does not interrupt an in-flight turn. Resume continues the same step. Skip invalidates the selected current turn, records it as skipped, and moves to the next step; a late post to a skipped turn is rejected. End early ends the run and removes only its own queued step; an already active turn may finish normally without advancing the ended run. If the target is offline or loses its session, the step remains visible and queued for rejoin or lead skip. On room archive the run ends. Use transactional state checks and the existing idempotent post/pass semantics to handle replay and restart; no automatic advancement on duplicate calls.

The room header offers a setup dialog for format, slots, rounds and topic, plus a persistent run panel with current step and Pause/Resume, Skip and End controls. Marker messages are system-labelled, do not impersonate the lead or create extra turns, and the banner tells a reviewer not to edit without altering actual permissions. Document the interaction with ordinary queued work and the advisory nature of the feature.

## Validation

For locks: competing agents in separate rooms, same-holder renewal, ownership checks, expiry, restart/replacement/end/archive cleanup, edit permission, force-release, event visibility and concurrent acquisition. For formats: both plans and round counts, slots/validation, ordered execution and banners, lead interruptions, queued work, replay/duplicate posts, passes, final proposals, pause/resume/skip/end, offline/rejoin and a real database/server reopen. Exercise controls in an isolated browser and run `npm run check` before each commit.
